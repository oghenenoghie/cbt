# ADR 0007: Offline exams on lab computers

- **Status:** Accepted. Stages A to D are built.
- **Date:** 2026-11-15
- **Implemented in:** `backend/api/app/offline/`, `backend/api/app/models/offline.py` (migration `0016_offline_exams`); the web screens in `apps/web` (`/school/lab-computers`, the exam page's Lab computers card, `src/lib/offline.ts`); the lab app in `apps/desktop`

## Context

Many schools sit exams in computer labs whose internet is slow, shared or absent. The product docs plan a Windows desktop app for this (`docs/architecture/overview.md` §4, requirements "Desktop and offline"): it downloads a **signed exam package** while online, lets students sit the exam with answers saved locally after every change, seals each submission and uploads it **idempotently** when the connection returns, and the server **validates every submission** because the device is untrusted. They left open how students sign in offline, whether answer keys may leave the server, how packages travel, and which exams can be sat offline.

The user decided these on 2026-11-15:

- **Signing in:** one-time **exam codes**. The teacher prints a code for each student for an exam; the student signs in on the lab computer with their username and that code. Passwords never leave the server, and a code is useless after the exam (chosen over carrying password hashes, or the invigilator picking the student).
- **Answer keys:** they stay on the server and answers are marked after upload, **unless an exam's author opts in** to instant scores on lab computers, which puts that exam's key, encrypted, on them. Off by default; the approver sees the choice.
- **Transfer:** **over the internet, and by USB file** for labs that never go online.
- **Which exams:** **every published exam can be sat offline unless its author turns that off.**

The work is built in stages:

- **A. The API:** the exam settings, lab computer registration, exam codes, signed packages, and checked, idempotent upload of results. (Built.)
- **B. Web screens:** the settings, printing codes, managing lab computers, USB export and import, and each exam's offline status. (Built.)
- **C. The desktop app:** setting up a computer, downloading and checking packages, students signing in with codes, sitting with crash-safe local storage, instant scores where allowed, and syncing. (Built.)
- **D. Packaging:** the Windows installer, updates and a CI build (decision 10). (Built.) School network (LAN) mode is later; nothing here assumes the sync server is the cloud.

## Decisions

1. **Exam settings.** `offline_allowed` (default on) and `offline_instant_scores` (default off), set while the exam is a draft and frozen with it. Instant scores need results shown as soon as each student submits (`results_release = "immediate"`): otherwise a lab computer would show a score the school hasn't released. Submitting an exam that breaks this is refused with the reason.

2. **Lab computers are registered by a school admin**, and each has its own key pair.
   - **Online:** the admin creates a one-time registration code (valid 24 hours). The desktop app sends it with the school code, a name and the public half of a key pair it generated; the private half never leaves the computer. It gets back a device token (stored by the server only as a SHA-256 hash), the server's package-signing public key and the school's offline key (decision 5).
   - **By file (USB):** the desktop app writes a registration request (name and public key); the admin uploads it in the web app and gets a setup file to carry back (device id, school, signing public key, school offline key). No token: such a computer never talks to the server.
   - Admins list, rename and **revoke** lab computers. A revoked computer can't download packages or upload results.

3. **Exam codes** are generated by the people who can release the exam's results (its author, its subject's teachers in its classes, school admins), for every student it is set for, or again for chosen students (a lost slip). Each is 8 characters from an alphabet without look-alike characters, shown once for printing, and stored only as a salted PBKDF2-SHA256 hash (200,000 iterations), which the package carries so the lab computer can check a code offline. Generating codes again replaces the earlier ones; packages downloaded before that keep the old codes, so the computer must download again.

4. **Packages are signed by the server** with Ed25519 (`OFFLINE_SIGNING_KEY`; development servers generate and keep one under `STORAGE_DIR`). A package is an envelope: the JSON body as text, and the signature over exactly those bytes, so nothing depends on two languages formatting JSON the same way. The body holds the exam's settings, the frozen paper without answer keys or explanations, passages, and the students it is set for (id, username, name, class and code hash). Each download is recorded (`offline_packages`) with the paper's fingerprint and the student list, for checking results later. A package is available from 14 days before the exam opens until it closes, once codes exist.

5. **Instant scores** put the exam's answer keys in the package encrypted with AES-256-GCM under the school's offline key, which only registered lab computers hold. A package copied off a USB stick doesn't reveal the keys; a determined person with a registered computer could. That is the trade the author opts into, and the setting says so. Essays still wait for a teacher, and the server's marking after upload is what counts.

6. **Results upload as signed submissions**, from the device over the internet or in a results file a teacher uploads in the web app. Each has a client-made id (the idempotency key) and is signed by the lab computer's key. The server checks:
   - the lab computer is registered to the school and not revoked, and the signature is valid;
   - the package was issued for this exam and its paper is the exam's frozen paper;
   - the student was in the package, the question and option orders match the paper, and each answer fits its question's type;
   - the times: started within the exam's window and finished within the duration (with a small allowance). A lab computer's clock can be wrong or changed, so times outside are **flagged** for staff rather than refused.

   An accepted submission becomes an attempt (`source = "offline"`) with its answer events, marked by the same code as online attempts. **The same submission again returns the first result**; the same id with different content is refused and recorded. A student who already used all their attempts, or is sitting online at that moment, gets a **conflict**: kept for staff, not counted. So does a result that arrives after the exam's results were released, because released results are final and their marking is locked. A result for an exam withdrawn after its package was downloaded is rejected.

7. **Files carried by USB** are JSON. A package and a setup file are the signed envelope itself. A registration request is an envelope of format `cbt-device-request/1` whose body holds the computer's `name`, `public_key` (Ed25519) and `exchange_key` (X25519), signed by its own key. A results file is `{"format": "cbt-offline-results/1", "submissions": [envelopes]}`; the web app also takes a list of results or a single one, and uploads them 2,000 at a time. The web app only finds the envelopes in a file; the API checks each one.

8. **Who sees what on an exam.** The exam reports `manage_offline` among its `allowed_actions` to the people who can release its results, while it is published and can be sat on lab computers: they make codes and export packages until it closes, and upload results at any time. Its offline status (codes, downloads, results) is shown to everyone who can see the exam, with each student's code batch but never a code.

9. **The lab app** (`apps/desktop`, stage C). The user decided on 2026-11-15 that the exam room is locked, and that a lab PIN on each computer guards the staff side.
   - **Structure.** The main process does everything that matters: keys, files, the network, signing and checking. The window only shows screens, through a narrow bridge (`contextIsolation`, `sandbox`, no Node in the window).
   - **The exam room is locked.** The app runs full screen and on top. Closing it, other windows and leaving the page are blocked, and only the lab PIN unlocks it, for example after a crash or for a student who must leave. An app can't block everything Windows offers (Ctrl+Alt+Del, for one), so invigilators still matter. Development builds run in a normal window.
   - **The lab PIN** (at least 6 digits) is set when the computer is registered and kept only as a scrypt hash. The staff side (downloading exams, loading a USB package, sending and saving results) needs it. Wrong PINs lock it for a minute, then longer.
   - **Local storage** is a folder of files in the app's data directory, not SQLite:
     - `device.json`: the computer's id, school, the signing key and the server address. The device token, the private key and the school key are encrypted with Windows DPAPI (Electron `safeStorage`).
     - Packages as downloaded, signed. Each is checked again every time it is loaded.
     - One journal per attempt. Every answer is appended and flushed to disk before the screen says it is saved, which makes the history append-only by construction and needs no native module.
     - An outbox of sealed results until the server has answered.
   - **Trust.** Online registration trusts the server over HTTPS. A USB setup file carries the signing key and is trusted on first use, because a school admin brought it from the web app. Every package must verify against that key and belong to the computer's school.
   - **Sitting.** A student chooses an exam that is open, then signs in with their username and exam code, checked against the package's hashes. Wrong codes are throttled per student. Attempts count those the server knew about when the package was downloaded, plus those on this computer. The question and option orders follow the online rules: passages move with their questions, and true/false options stay in order. The computer's clock runs the attempt: it ends at the start plus the duration, capped at closing, and a restart carries on from the saved start. The server flags times it doesn't believe (decision 6).
   - **Instant scores** decrypt the exam's key with the school key and mark it with the same rules as the server. The score shown is for the student only: the server marks the uploaded answers again, and that mark is the one that counts.
   - **Sending results.** A computer registered online uploads its outbox every minute and on request, and shows what the server decided for each result. Staff can save results to USB at any time. When a computer online finds an exam is no longer offered (withdrawn), it stops students starting it.

10. **Installing and updating the lab app** (stage D). The user decided on 2026-11-15 that updates come from the school's own server, and that installers are unsigned until the school has a code-signing certificate.
    - **The installer** is built by CI on Windows with electron-builder: an NSIS installer for all users of the computer. It is unsigned for now, so Windows warns about an unknown publisher on each install. The build signs it once a certificate and its password are added as GitHub secrets.
    - **A release** is published to the server with `python -m app.cli publish-lab-app <installer> --version x.y.z`. This keeps the installer in `LAB_APP_DIR`, plus a manifest (version, file, size, SHA-256, notes) signed with the package-signing key. That is the key lab computers already trust, so a lab computer installs only what the school's server signed, even without code signing. The newest two installers are kept.
    - **School admins** download the installer from the web app's Lab computers page, for a first install and for computers that never go online.
    - **Lab computers registered online** check for a new version with each sync. They download it in the background, check its signature and SHA-256, and wait. Staff install it from the staff side, and never during an exam: installing is refused while any attempt on the computer isn't handed in. Updating keeps the registration, packages, attempts and results, which live in the user's data folder, not the program's.
    - **Computers registered by USB** are updated by closing the app from the staff side and running the new installer from a USB stick.

11. **Limits, stated plainly.** Offline mode can't give live invigilation or immediate revocation: a revoked student or a withdrawn exam isn't known to a lab computer until it syncs, and its clock can be wrong. Staff see flags and conflicts; schools should cover the rest in their exam rules.

## Consequences

- No password, long-lived user token or platform secret is on a lab computer. A device token is per computer and revocable.
- An offline attempt counts like an online one in results, marking and release.
- Packages can be large for long papers with passages; there are no images yet.

## Still open

- Rotating the school offline key and the signing key.
- Showing a computer's live state (which students have handed in) to staff while it's offline.
- School network (LAN) mode, and diagrams or images in packages.
